# ADR 0001 · 工具调用协议：原生 tool_calls 为主，文本动作降级为抢救通道

- 状态：已接受
- 日期：2026-10-03
- 关联：F-35（ReAct 循环）、F-39（动作流解析）、F-40（虚拟动作闭环）、F-41（工具注册表）
- 取代：无
- 对应 spec §6 的 G7

## 背景

F-35 规定使用 provider 原生的 `tool_calls` 协议（`assistant.tool_calls` +
`tool.tool_call_id`），而 F-39 规定从模型**原始文本**里解析 JSON 动作，F-40 又为虚拟动作
定义了"伪造 ok 结果回灌"。两者都能表达"模型要求执行一个动作"，但机制完全不同：

- 原生协议由 provider 校验，`id` / `name` / `arguments` 结构化，不存在解析歧义；
- 文本协议是启发式的：要处理代码块围栏、多对象连写、尾随逗号、截断、以及超大整数不丢精度。

若两者并列成"两条执行通道"，运行时会含糊于"谁是权威"，且两条路径的 observation 回灌
格式不同，历史里会混入两种形状——这会同时伤害可读性与前缀缓存。

## 决策

**原生 `tool_calls` 是唯一的执行通道；F-39 的解析器降级为抢救通道（scavenge）。**

1. 所有能力（含 F-40 的虚拟动作）一律注册为 F-41 注册表里的工具，带原生 schema。
2. ReAct 循环只消费原生 `tool_calls`。
3. F-39 的解析器保留，但只在**模型把动作吐在文本里**时兜底。这不是理论风险：
   DeepSeek 思考模式会把工具调用吐在 `reasoning_content` 里而最终 `tool_calls` 为空。
   兜底命中时同样转成 `[]Action`，走同一条执行路径与同一种回灌格式。
4. F-40 的虚拟动作就是普通工具，其"伪造 ok"就是一条正常的 `tool` 消息（带
   `tool_call_id`），天然契合原生协议，不需要第二套机制。
5. 配置面：`agent.protocol: native | auto`，默认 `auto`（原生为主 + F-39 兜底）。
   `native` 用于排查"兜底是否在掩盖 provider 侧问题"。

## 后果

正面：

- 执行路径只有一条，`[]Action` 是唯一内部表示，历史里只有一种 observation 形状
- 虚拟动作不需要第二套协议
- F-39 仍是必要的：它防的是真实失效模式，且已有 8 组表驱动测试

代价：

- 必须对"文本兜底是否触发"做观测（日志 + 指标），否则兜底会长期掩盖 provider 侧问题
- `auto` 下同一次输出可能既有原生 `tool_calls` 又有文本动作，需要明确的去重规则。
  **决策：原生存在时忽略文本动作，并记一条告警**

## 备注

F-39 的 ticket（29）已 resolved，解析器在 M1 已落地并有测试。本决策不要求重写它，
只要求它不再是**并列通道**。

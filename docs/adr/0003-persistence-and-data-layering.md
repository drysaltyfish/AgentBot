# ADR 0003 · 持久化选型与数据分层

- 状态：已接受
- 日期：2026-10-03
- 关联：F-38（历史存储）、F-47（记忆抽象）、F-48（长期记忆）、F-50（向量检索）、F-83~F-89、决策 11、决策 16
- 取代：无
- 对应 spec §11 新增登记项

## 背景

M1 起对话历史与长期记忆都用 JSONL 文件（`FileHistory` / `HistoryMemory`），
在 M2 收敛为"进程内 + 可选落盘"。这在当时是对的：写入是单进程顺序追加，
读是"整段取出"，文件语义与需求完全匹配，且零依赖。

M2 结束后，需求变了：

1. **按条件读取**。`recall_history` 现在把整个会话历史读进内存再子串过滤；
   历史越长，这个 O(n) 扫描越浪费，而且无法按时间/角色/来源筛选。
2. **检索质量**。子串匹配对中文的召回很差：用户问"之前说过的那个乐队"，
   子串匹配无能为力。
3. **字段演进**。记忆已经历一次字段变化（长度上限、作用域、去重判据）。
   每次都要"读旧文件、转新结构"，而 JSONL 没有版本概念。
4. **可观测性**。缓存命中率与 token 消耗只进日志，不能查询、不能回归。
5. **隐私动作**。"忘记这条"目前做不到——文件里没有可寻址的条目。

同时有一条不能破的约束：**部署形态是单二进制 + 同目录配置**（决策 16）。
引入数据库服务端会直接破坏它。

## 决策

**引入嵌入式 SQLite（`modernc.org/sqlite`，纯 Go，无 cgo）作为唯一持久层；
文件退化为导入/导出格式，不再是主存储。**

数据按"生命周期"分层，而不是按功能分层：

| 层 | 表 | 生命周期 | 读特征 |
|---|---|---|---|
| 消息流 | `messages` + FTS | 与会话同寿，可归档 | 范围扫描 + 全文检索 |
| 会话台账 | `sessions` | 长期，只累加 | 点查 + 聚合 |
| 长期记忆 | `memories` | 长期，可增删改 | 按作用域检索 |
| 在途状态 | `pending` | 短，到期即清 | 点查 + 扫描过期 |
| 提示词快照 | `prompt_snapshots` | 短，环形保留 | 点查（回放） |

关键取舍：

- **一个库而不是每个功能一个库**：SQLite 的跨表事务让我们能做"消息写入 + 台账累加"
  的原子提交。多个文件做不到。**这是选型的核心理由，不是"图省事"。**
- **WAL + 短 `busy_timeout` + 应用层抖动重试**：默认的长超时会让并发写者
  按同一节奏退避，形成护航效应。短超时 + 随机抖动让写者错开。
- **声明式加列、版本链管数据迁移**：绝大多数 schema 变更只是加列，用对账就能幂等完成；
  把版本号留给真正需要动数据的变更，避免迁移链被无意义的版本号淹没。
- **消息存"实际发送的报文"的旁路快照**：缓存收益完全建立在"前缀逐字节不变"上，
  而目前只能从日志反推。留一份可重放快照，才能把"前缀稳定性"变成回归测试。

## 后果

正面：

- 检索、聚合、事务都变成 SQL，不再有"读全文件再筛"
- 单一迁移机制，字段演进有版本可循
- 缓存与用量可查询、可回归，F-74 的指标不再依赖外部系统
- 记忆具备可寻址条目，遗忘/导出成为可能
- 仍是单文件 + 单二进制，部署形态不变

代价：

- 引入一个较大的依赖（纯 Go，无 cgo，但体积不小）
- 需要自己承担写竞争、WAL 增长、迁移失败这些数据库运维问题
- JSONL 的"直接用文本编辑器看"的优点消失，需要提供导出命令补偿
- 既有 JSONL 需要一次性导入

## 备选方案与否决理由

- **继续用 JSONL，自己实现索引**：等于手写一个劣质数据库。检索、事务、并发都要
  自己保证，而这些正是最容易出错的地方。否决。
- **引入外部数据库服务**：破坏决策 16 的单二进制形态，也把"自用机器人"变成
  "需要运维的部署"。否决。
- **每个功能一个独立文件/库**：无法做跨表事务，且迁移机制要重复多套。否决。
- **只做记忆落库、历史继续用文件**：历史恰是检索需求最强的一方，且
  `recall_history` 已经因此变成摆设（见 ticket 43 补记）。否决。
